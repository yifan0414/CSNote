# Agent 意图识别：规则、小模型还是大模型？

## 面试题

> Agent 的意图识别应该使用规则、小模型，还是直接使用大模型？

## 先说结论

生产环境通常不应该三选一，而应该采用**混合路由**：

- 规则负责确定性强、风险高、必须可控的场景；
- 小模型负责高频、边界稳定的主要意图；
- 大模型负责语义复杂、上下文相关和长尾意图；
- 最后结合置信度、歧义度和动作风险，决定直接执行、向用户澄清，还是请求人工确认。

核心不是“哪个模型最准”，而是在准确率、延迟、成本、可维护性和错误执行风险之间取得平衡。

## 30 秒回答

> 我不会在规则、小模型和大模型之间只选一个，而会设计分层的混合路由。规则适合明确命令、权限限制和高风险动作；小模型处理标签稳定、调用量大的主流意图，成本低、延迟也更可控；大模型处理模糊表达、上下文依赖和长尾问题。路由结果还要经过置信度与风险门控：高置信度、低风险才直接执行；存在歧义就追问；退款、删除、转账等高风险工具即使识别置信度很高，也必须做参数校验、权限检查和用户确认。最终我会重点评估错误执行率、任务成功率、拒识率、P95 延迟和单次调用成本，而不只看意图分类准确率。

## 2 分钟展开回答

### 1. 为什么不能只使用规则？

规则的优点是确定、快速、便宜、容易审计，适合：

- `/help`、`取消订单` 等明确指令；
- 黑白名单、权限和合规限制；
- 对输入格式有严格要求的流程；
- 风险动作执行前后的校验。

但自然语言表达存在同义改写、上下文省略和组合意图。规则数量增长后容易冲突，维护成本会快速上升，也很难覆盖长尾表达。

### 2. 为什么需要小模型？

当业务意图集合相对固定、标注数据充足、调用量较大时，小型分类模型通常是主路由的高性价比方案：

- 延迟和成本稳定；
- 输出标签空间受控；
- 便于针对每个意图评估 precision、recall 和混淆关系；
- 可以私有化部署，降低敏感数据外发风险。

它的局限是依赖标注数据，对新意图、分布漂移、复杂上下文和多意图输入的适应能力有限。

### 3. 为什么还需要大模型？

大模型更适合：

- 用户表达模糊，需要结合多轮上下文判断；
- 意图标签无法提前完整枚举；
- 一个请求包含多个目标，需要拆解任务；
- 需要根据工具描述进行语义路由；
- 小模型低置信度或检测到分布外输入。

但大模型不能被视为天然可靠的执行控制器。它的成本和延迟更高，输出还可能受到提示注入、上下文污染和幻觉影响，因此不能仅凭一次模型判断直接执行高风险动作。

## 更接近生产环境的架构

```text
用户输入
   ↓
安全过滤、身份与权限检查
   ↓
低成本路由：规则 / 小模型 / 向量检索
   ↓
置信度、歧义度、分布外检测与动作风险判断
   ├─ 高置信度 + 低风险 → 进入确定性业务流程
   ├─ 复杂语义或长尾问题 → 大模型进一步判断
   └─ 低置信度或高风险 → 追问 / 用户确认 / 人工处理
   ↓
工具参数、权限、业务约束和幂等性校验
   ↓
执行工具
   ↓
日志、审计、监控与反馈数据回流
```

关键点是：**规则并不只是第一层。**规则和策略通常同时存在于输入、路由、工具调用前和工具执行后。

## 方案对比

| 方案 | 优点 | 局限 | 适合场景 |
|---|---|---|---|
| 纯规则 | 快、便宜、确定、可审计 | 长尾覆盖差，规模扩大后难维护 | 明确指令、权限、合规、高风险校验 |
| 小模型分类 | 延迟低、标签受控、容易量化评估 | 依赖数据，对新意图和复杂上下文较弱 | 客服、工单、固定业务流程的高频意图 |
| 大模型路由 | 泛化和上下文理解能力强 | 成本高、结果不完全确定、有安全风险 | 长尾意图、多轮理解、任务拆解、开放工具集 |
| 混合架构 | 兼顾效果、成本与安全 | 系统设计和运维更复杂 | 大多数生产级 Agent |

## 置信度与风险门控

不要把“模型置信度高”等同于“操作安全”。可以把决策拆成两个维度：

| 意图置信度 | 动作风险 | 建议策略 |
|---|---:|---|
| 高 | 低 | 自动执行 |
| 低 | 低 | 追问或进入大模型兜底 |
| 高 | 高 | 展示动作名称和参数，请求明确确认 |
| 低 | 高 | 禁止执行，先澄清，必要时转人工 |

阈值也不应全局固定。查询天气和删除生产数据不能使用相同的自动执行标准；应根据意图、语言、渠道和动作风险分别在验证集与真实流量上调优。

## 面试中应该主动提到的指标

### 模型与路由效果

- 各意图的 precision、recall、F1，而不是只看整体 accuracy；
- 混淆矩阵，尤其关注容易导致错误动作的意图对；
- 拒识率、澄清率和有效覆盖率；
- 新意图和分布外输入的识别能力。

### 业务效果

- 任务完成率和用户一次解决率；
- 错误执行率，尤其是不可逆操作的错误执行率；
- 人工接管率和 fallback 后的恢复率；
- 用户纠正、撤销和投诉比例。

### 工程指标

- P50/P95/P99 延迟；
- 单次请求和单个成功任务的成本；
- 模型超时、工具失败和重试率；
- 数据漂移、意图分布变化和版本回归。

## 常见追问

### 为什么不全部交给大模型？

> 如果工具很少、流量不大、风险较低，LLM-first 可以减少早期开发成本。但在高流量或高风险系统中，全部交给大模型会带来延迟、成本、稳定性和审计问题。因此我会把明确且高频的意图下沉到规则或小模型，把大模型能力集中在真正需要语义泛化的部分。

### 为什么不全部使用小模型？

> 小模型适合封闭标签体系，但真实用户会提出未见过的问题，也会省略上下文或组合多个目标。强行分类会产生错误执行，所以需要拒识机制，并把复杂或分布外请求交给大模型或澄清流程。

### 如何设置置信度阈值？

> 我会先根据离线验证集画出 precision-recall 或 coverage-risk 曲线，再按动作风险设置不同阈值，然后通过灰度流量观察错误执行率和澄清率。阈值不是一次设定后不变，还要随着数据漂移持续校准。

### 如何处理小模型和大模型结论不一致？

> 不应该简单采用多数投票，而要根据风险与证据决策。低风险请求可以采用经过验证的主路由；高风险请求只要出现冲突就进入澄清或确认流程，同时记录样本用于后续分析。

### 如何防止 Agent 调错工具？

> 我会把“选择工具”和“允许执行”拆开。模型只负责提出工具调用建议，真正执行前还要进行工具白名单、参数 schema、用户权限、业务约束和幂等性检查。敏感或不可逆动作必须要求用户确认，并保留审计日志。

### 新意图出现后怎么办？

> 先通过 fallback、用户纠正和人工接管日志发现聚类，再判断它是已有意图的表达变化，还是需要新增标签。如果是稳定高频的新意图，可以补充数据并下沉到小模型；仍然零散的长尾请求则继续由大模型处理。

## 项目经验回答模板

> 在我的项目中，业务有 **[意图数量]** 类主要意图，其中 **[高频比例]** 的请求集中在少数固定流程。为了兼顾成本和安全，我先用 **[规则/小模型]** 处理确定性和高频意图，并设置拒识与歧义检测；对于低置信度、上下文相关或长尾请求，再交给大模型判断。涉及 **[退款/删除/发信等动作]** 时，即使分类置信度很高，也必须经过权限、参数和用户确认。上线前我使用 **[离线指标]** 评估分类效果，上线后重点监控 **[错误执行率、完成率、P95 延迟和成本]**。最终实现了 **[量化结果]**。

回答时最好补充真实数字，例如：

- 覆盖了多少类意图；
- 自动处理覆盖率提高了多少；
- P95 延迟或调用成本降低了多少；
- 错误执行率或人工接管率下降了多少。

## 容易失分的回答

- 只比较模型准确率，不谈错误执行风险；
- 把规则、小模型和大模型描述成必须严格串行的三层；
- 把模型输出的 confidence 直接当作真实概率；
- 认为高置信度就可以自动执行任何工具；
- 只讲离线准确率，不谈业务成功率、线上漂移和成本；
- 没有 fallback、澄清、人工确认和审计机制。

## 一句话记忆

> 规则保证确定性，小模型承接高频，大模型覆盖长尾；置信度决定是否澄清，风险等级决定是否允许执行。
