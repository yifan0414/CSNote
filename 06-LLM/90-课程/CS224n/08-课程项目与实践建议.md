# CS224N 08：课程项目与实践建议

> [!abstract] 本节定位
> 理解默认 GPT 项目和自定义研究项目的范围，学习选题、基线、实验、评估和报告设计。

## 学习目标

- [ ] 在默认项目与自定义项目间做出合理选择
- [ ] 把宽泛想法收窄为可证伪问题
- [ ] 规划基线、对照、消融、评测与时间预算

## 知识笔记

> [!info] 课件范围
> 对应 Final Projects & Practical Tips PPT 第 12–53 页，并结合官网项目说明。重点不是某个模型公式，而是如何把 NLP 想法变成可完成、可比较、可复现的研究项目。

## 1. 项目评价的对象

课程项目不是只看最终分数。完整研究工作包括：

1. 问题是否清楚；
2. 相关工作是否准确；
3. 方法是否与问题匹配；
4. 数据和评测是否可信；
5. 实验能否支持结论；
6. 分析是否解释成功与失败；
7. 报告是否可复现。

高分模型不一定是好项目；一个结果为负但设计严谨、分析充分的研究也可能很有价值。

## 2. Default 与 Custom Project

### 2.1 Default Project

默认项目围绕 GPT 类模型的实现、预训练和下游适配展开。优势：

- 问题和代码骨架更明确；
- 更容易控制工作量；
- 能系统练习 Transformer、优化和 fine-tuning；
- 不需要从零寻找数据与指标。

适合希望把重点放在技术实现与实验基本功的同学。

### 2.2 Custom Project

自定义项目从研究问题出发，允许：

- 新任务或新数据；
- 对已有方法做系统比较；
- 改进模型、训练或评测方法；
- 分析模型行为；
- 将 NLP 应用于新领域。

它要求团队自己承担范围、数据、算力和评测风险。

> [!important]
> 自定义项目的自由度不是“做得越大越好”。课程周期很短，最重要的是一个可完整验证的小问题。

## 3. 从题目到研究问题

宽泛题目：

> 我想研究 RAG。

可检验问题：

> 在固定生成器和上下文预算下，加入 cross-encoder reranker 是否能提高多跳问答的答案准确率与引用支持率？

后一种表述明确：

- 操作变量：是否使用 reranker；
- 控制变量：生成器和上下文预算；
- 任务：多跳问答；
- 指标：答案准确率、引用支持率；
- 可证伪结果：两项指标可能不提升。

### 问题定义模板

1. **对象**：研究什么模型、数据或行为？
2. **干预**：改变哪个因素？
3. **比较**：与什么 baseline 比？
4. **测量**：用什么指标与统计？
5. **边界**：结论只适用于哪些设置？

## 4. 常见项目类型

### 4.1 实现和复现

复现论文核心结果并分析与原文的差异。

价值不在“跑通代码”，而在：

- 明确不可复现的细节；
- 控制数据和计算预算；
- 验证结论对不同设置是否稳定。

### 4.2 方法比较

在同一数据、预算与评测下比较两个或多个方法。

必须避免：

- 一个方法充分调参、另一个使用默认参数；
- 使用不同基座模型；
- 训练 token 或 API 预算不同；
- 只汇报最好一次运行。

### 4.3 小幅方法改进

在已有模型上加入一个可解释改动。关键是：

- 有清晰动机；
- 有无该组件的消融；
- 参数量与计算量公平；
- 分析何时有效、何时无效。

### 4.4 新领域应用

将已有 NLP 方法用于法律、医疗、教育、社科或专业文档。

主要研究风险往往不在模型，而在：

- 标签与任务定义；
- 数据许可和隐私；
- 领域专家验证；
- 评价指标是否反映真实用途。

### 4.5 分析型项目

不提出新模型，而研究：

- 错误模式；
- 公平性；
- 鲁棒性；
- 记忆与污染；
- prompt 敏感性；
- 可解释性。

分析型项目同样需要假设、对照和统计，而非只展示几个案例。

## 5. Proposal

课件要求 proposal 清楚回答：

- 要解决什么问题；
- 为什么重要；
- 相关工作是什么；
- 使用什么数据；
- 至少一个 baseline；
- 方法或比较设计；
- 如何评测；
- 团队分工和时间计划。

### 最小可行项目

在 proposal 阶段先定义 Minimum Viable Project：

1. 数据可读；
2. baseline 可运行；
3. 主指标可计算；
4. 一张结果表可生成；
5. 即使新方法失败也能形成分析。

扩展目标应与最小项目分开，不能让全部成果依赖最后一周才完成的高风险组件。

## 6. Milestone

Milestone 应证明项目已从计划进入证据阶段：

- 数据已经获得并清洗；
- baseline 有初步结果；
- 主要代码路径能端到端运行；
- 当前失败和风险已识别；
- 后续计划根据实际结果调整。

只汇报“读了论文、搭了环境”不足以证明研究问题可在截止前完成。

## 7. 论文式写作

典型结构：

1. Abstract；
2. Introduction；
3. Related Work；
4. Approach；
5. Experimental Setup；
6. Results；
7. Analysis；
8. Conclusion；
9. Limitations / Ethics。

### Introduction 的逻辑

- 问题是什么；
- 现有方法为何不足；
- 本文做了什么；
- 主要发现是什么。

不要等到结果部分才第一次说明贡献。

### Related Work

不是论文列表，而是按方法或观点组织差异：

- 哪些工作解决相同问题；
- 使用什么假设；
- 与本项目的关键区别；
- 本项目借用了哪些组件。

## 8. 如何找研究切入点

课件建议从最新会议、论文结尾和真实痛点寻找问题。

可靠来源包括：

- ACL Anthology；
- arXiv；
- ACL、EMNLP、NAACL、TACL 等会议或期刊；
- 论文引用和被引关系；
- 作者代码与数据；
- 现有 benchmark 的 failure cases。

### 从论文中找问题

重点读：

- Limitations；
- Error Analysis；
- Ablations；
- Future Work；
- 对数据和算力的假设；
- 只在单一模型或数据集上成立的结论。

## 9. 数据选择

### 9.1 先问许可和来源

需要记录：

- 数据由谁创建；
- 许可是否允许研究和再发布；
- 是否包含个人信息；
- 标签如何产生；
- 是否有已知偏差；
- 是否与预训练或测试集重叠。

### 9.2 划分

- train：拟合参数；
- validation/dev：选择模型和超参数；
- test：最终一次或少数几次评估。

不得根据 test 结果反复改模型，否则 test 已变成 dev。

若多个样本来自同一用户、文档或事件，应按组划分，避免高度相似内容跨集合泄漏。

### 9.3 数据量不等于信息量

重复、模板化或机器生成的样本可能让数量很大但有效多样性很低。应检查：

- 去重；
- 长度和标签分布；
- 来源分布；
- 语言和领域覆盖；
- 难度；
- 时间分布。

## 10. Learning Curve

训练集规模为 $n$ 时记录 dev 性能：

$$
\{(n_i,\operatorname{score}_i)\}_{i=1}^{K}.
$$

曲线可判断：

- 数据不足：性能随数据持续上升；
- 模型或目标受限：很早进入平台；
- 高方差：不同运行差距大；
- 数据质量问题：增加数据反而下降。

Learning curve 比单个最终数字更能说明下一步应增加数据还是改变方法。

## 11. Baseline 与消融

### Baseline 层次

1. 随机或多数类；
2. 简单词袋/线性模型；
3. 标准预训练模型；
4. 最接近的公开方法；
5. 计算预算相当的强基线。

### Ablation

若完整系统由 $A+B+C$ 组成，至少比较：

- $A+B+C$；
- 去掉 $B$；
- 去掉 $C$；
- 必要时只保留核心组件。

消融回答“提升来自哪里”，而 baseline 回答“是否优于已有选择”。

## 12. 实验统计

神经网络结果受：

- 随机初始化；
- 数据顺序；
- dropout；
- 非确定性内核；
- checkpoint 选择

影响。

应尽量报告多随机种子：

$$
\bar x
=
\frac{1}{K}\sum_{k=1}^{K}x_k.
$$

同时给标准差、置信区间或配对显著性检验。资源有限时也应说明只运行一次造成的不确定性。

## 13. 错误分析

不要只看平均分。建立错误类别，例如：

- 长输入；
- 罕见实体；
- 否定或反事实；
- 多跳推理；
- 检索缺失；
- 格式不合规；
- 特定语言或领域。

可构造矩阵：

| 错误类型 | Baseline | 新方法 | 变化 |
| --- | ---: | ---: | ---: |
| 检索缺失 | 40 | 25 | 改善 |
| 推理错误 | 20 | 22 | 未改善 |
| 格式错误 | 5 | 12 | 变差 |

这样才能说明系统为何改变，而非只说明总分改变。

## 14. 使用预训练模型和生成式 AI

即使允许调用现有模型，也必须记录：

- 模型与版本；
- API 日期；
- system/user prompt；
- temperature 与 decoding 参数；
- 重试和失败处理；
- 成本；
- 数据是否发送给外部服务。

课程的学术诚信规则优先于工具能力。AI 工具可以辅助开发，但不能替代应由学生完成的作业或报告贡献。

## 15. 项目复现清单

> [!check]
> - 固定或记录随机种子；
> - 保存环境和依赖版本；
> - 保存数据处理脚本；
> - 记录训练命令和超参数；
> - 明确 checkpoint 选择规则；
> - 保存原始预测；
> - 结果表可由脚本重新生成；
> - 报告失败实验，而不只报告最好结果。

## 16. 小结

- 好项目是可验证问题，不是技术名词的堆叠。
- 先完成最小 baseline 和评测闭环，再增加复杂组件。
- 数据许可、划分、泄漏和质量决定结论能否成立。
- Baseline、消融、learning curve、随机种子和错误分析共同构成证据。
- 报告的价值在于让读者理解做了什么、为何有效以及边界在哪里。

## 建议学习流程

1. 带着学习目标快速浏览 PPT、讲义或 Notebook，先建立本节地图。
2. 第二遍按核心提纲停下推导公式、追踪 shape 或复现代码。
3. 在指定阅读中寻找课件结论的实验依据、假设和适用边界。
4. 不看资料回答自测题，将答不清的点写入学习记录。
