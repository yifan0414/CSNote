# CS224N 16：推理（二）：加速、长上下文与测试时扩展

> [!abstract] 本节定位
> 串联 speculative decoding、off-policy drift、on-policy distillation、长上下文和 inference-time scaling。

## 学习目标

- [ ] 解释 speculative sampling 的接受和校正逻辑
- [ ] 区分 on-policy、off-policy、online 与 offline
- [ ] 分析长上下文与测试时计算的收益和成本

## 知识笔记

> [!info] 课件范围
> 对应 Reasoning 2 PPT：speculative decoding、online/offline 与 on/off-policy、异步 RL 漂移、on-policy distillation、RoPE 与长上下文扩展、test-time compute scaling。

## 1. 推理阶段的串行瓶颈

自回归生成每次只能确定一个新 token：

$$
x_t\sim q(\cdot\mid x_{<t}).
$$

即使单次模型前向高度并行，时间轴仍是串行的。大模型每生成一个 token 都要执行完整网络，memory bandwidth 和 kernel launch 开销很高。

## 2. Speculative Decoding

使用：

- 小而快的 draft model，分布 $p$；
- 大而准确的 target model，分布 $q$。

流程：

1. draft 连续提出 $K$ 个候选 token；
2. target 一次前向并行计算这些位置的概率；
3. 按接受规则验证；
4. 在第一次拒绝处校正；
5. 继续下一轮。

核心收益来自：target 一次处理多个候选位置，而不是逐 token 调用。

## 3. Speculative Sampling 的接受规则

对 draft 采样 token $x_i\sim p_i$，target 给概率 $q_i(x_i)$。

接受概率：

$$
a_i
=
\min
\left(
1,
\frac{q_i(x_i)}{p_i(x_i)}
\right).
$$

若：

$$
u_i\sim U(0,1),\qquad u_i\le a_i,
$$

则接受 token。

若拒绝，从校正分布采样：

$$
q_i'(x)
\propto
\max(q_i(x)-p_i(x),0).
$$

这个 rejection-sampling 校正确保最终边缘分布与直接从 target $q$ 采样一致。

> [!important]
> Speculative decoding 的目标是减少 target 的串行调用，不是用小模型近似替换大模型；正确实现不会改变 target sampling 分布。

## 4. 接受率与速度

若平均每轮接受 $A$ 个 draft token，而 target 验证成本接近一次较大 batch 前向，则速度取决于：

- draft 生成成本；
- target 验证成本；
- 接受长度；
- batch size；
- 硬件利用率；
- KV cache 管理。

Draft 太弱：

- 候选经常被拒；
- 验证收益小。

Draft 太大：

- 接受率高；
- 但 draft 自身成本抵消收益。

最佳 draft 是速度与分布接近度的折中。

## 5. Dynamic 与 Universal Speculation

### Dynamic lookahead

不固定 $K$，根据：

- draft confidence；
- token entropy；
- 轻量 classifier；
- 最近接受率

决定继续 draft 还是交给 target。

容易 token 可多提，困难 token 提前验证。

### Universal speculative decoding

经典方法常要求 draft 与 target 使用相同 tokenizer。通用方法尝试处理不同 tokenizer 或通过字符空间、重编码和边界对齐验证。

## 6. 其他推理加速方向

课件列出 EAGLE、Sufia 等快速发展的 speculative 变体，思想包括：

- 在 feature space 预测候选；
- 树状提出多个分支；
- 用辅助头一次提出多个 token；
- 根据推理难度动态分配。

比较不能只看理论 accepted tokens，要测真实吞吐、延迟、batch 和输出等价条件。

## 7. Online/Offline 与 On/Off-Policy

这是两个不同坐标轴。

### Online vs Offline

- **Online RL**：训练时 agent 可继续与环境交互；
- **Offline RL**：只能使用预先记录的数据，不能探索新动作。

### On-policy vs Off-policy

- **On-policy**：训练 rollout 来自当前最新 policy；
- **Off-policy**：数据来自旧 policy、其他 policy 或人类。

> [!note]
> Online 系统也可能 off-policy：它持续与环境交互，但使用 replay buffer 中的旧经验训练。

PPO、REINFORCE、GRPO 按设计偏 on-policy；DQN 是典型 off-policy。

## 8. 为什么 LLM RL 会产生 Off-Policy Drift

大模型 rollout 与训练通常放在不同集群：

- inference 集群高吞吐生成；
- training 集群计算梯度；
- 权重通过网络异步同步。

Rollout 变旧的原因：

- 异步生成；
- 一个 batch 做多次梯度更新；
- 大 replay buffer；
- 参数传输延迟；
- 长回答生成期间 policy 已更新。

PipelineRL 甚至可在同一序列生成中途载入新权重，于是前后 token 来自不同 policy。

## 9. Off-Policy 的风险与缓解

风险：

- policy gradient 有偏；
- importance ratio 爆炸；
- reward hacking 被放大；
- stale data 与当前状态分布不匹配。

缓解：

- PPO clipping；
- 对 reference 的 KL penalty；
- 减少每批训练 epoch；
- 缩短 rollout 到更新延迟；
- 权重 streaming；
- in-flight update；
- 使用较少依赖 critic 的算法；
- 监测 rollout policy 与 train policy 的 KL。

系统吞吐与统计正确性存在真实权衡。

## 10. 标准知识蒸馏

Teacher 分布为 $P$，student 为 $Q$。

Forward KL：

$$
D_{\mathrm{KL}}(P\|Q)
=
\mathbb E_{x\sim P}
\left[
\log\frac{P(x)}{Q(x)}
\right].
$$

它是 mass-covering：teacher 有概率质量的区域，student 都被要求覆盖。

传统 KD 通常在 ground-truth 或 teacher 生成上下文上学习，因此相对 student 推理分布是 off-policy。

## 11. On-Policy Distillation

先让 student 自己生成上下文，再查询 teacher 对这些状态的软分布。

常使用 reverse KL：

$$
D_{\mathrm{KL}}(Q\|P)
=
\mathbb E_{x\sim Q}
\left[
\log\frac{Q(x)}{P(x)}
\right].
$$

特点：

- 上下文来自 student；
- 减少 train–test exposure mismatch；
- teacher 为 student 实际访问的状态提供稠密反馈；
- reverse KL 更偏 mode-seeking。

### 与 SFT/RL 比较

| 方法 | 上下文 | 信号 | 特点 |
| --- | --- | --- | --- |
| SFT | gold/固定数据 | 硬标签 | 便宜但 off-policy |
| 标准 KD | teacher 或 gold | 软分布 | 稠密但 teacher-centric |
| RL | student rollout | 稀疏 reward | on-policy 但昂贵 |
| On-policy KD | student rollout | teacher 软分布 | on-policy + 稠密 |

## 12. 领域适配中的蒸馏

在后训练模型上继续领域预训练可能破坏 instruction following。

一种混合：

- 70% 领域文本做 continual pretraining；
- 30% instruction data 做 on-policy distillation。

目标是在获得领域知识时，由 teacher 约束已有助手行为。

## 13. 为什么长推理需要长上下文

长上下文应用包括：

- 整个代码仓库；
- 数百页法律文档；
- 长期对话记忆；
- 数学中的多次尝试和回溯。

挑战：

1. 自然长文档数据稀少；
2. attention 计算和内存随长度增长；
3. 位置表示在训练长度外泛化差；
4. 支持长度不等于有效利用长度。

## 14. RoPE

RoPE 对 query 和 key 的二维通道对施加位置相关旋转：

$$
\tilde q_m=R_mq,
\qquad
\tilde k_n=R_nk.
$$

点积：

$$
\tilde q_m^\top\tilde k_n
=
q^\top R_m^\top R_nk
=
q^\top R_{n-m}k.
$$

因此注意力关系自然依赖相对距离 $n-m$。

特点：

- 只旋转 Q/K，不旋转 V；
- 保持向量范数；
- 在每层 attention 注入位置；
- 可结合插值和频率缩放扩展长度。

## 15. RoPE 长度扩展

### Position Interpolation

将长位置压缩回训练范围：

$$
m'
=
\frac{m}{s}.
$$

模型看到熟悉频率，但近距离位置也被压缩。

### NTK-Aware Scaling

调整旋转基频，不对所有频段做相同线性压缩，更好保留高频局部信息。

### YaRN

结合：

- 不同频段不同插值；
- ramp function；
- attention temperature 修正。

低频与高频承担的相对距离信息不同，因此分频处理。

## 16. 长上下文训练配方

课件总结四类做法。

### 16.1 Progressive Training

从 4K/8K 逐步扩到：

$$
8K\to32K\to64K\to128K.
$$

在每阶段做少量 continued pretraining 与 long-context instruction tuning。

### 16.2 Data Engineering

- 上采样书籍、代码库和长文档；
- 拼接相关文档；
- needle-in-a-haystack；
- 长程 QA；
- 多文档摘要；
- 自生成长上下文指令。

### 16.3 Attention Architecture

- sparse/sliding-window attention；
- global token；
- FlashAttention 降低 materialized attention memory；
- GQA/MQA 降低 KV cache。

> [!warning]
> FlashAttention 改善内存 IO 和中间存储，但标准 dense attention 的算术量仍为二次。

## 17. Test-Time Compute Scaling

不只扩展训练计算，也可在推理时投入更多计算。

策略：

- Best-of-$N$；
- weighted Best-of-$N$；
- sequential revision；
- beam search + process reward model；
- diverse search。

## 18. 验证器

### Outcome Reward Model

只判断最终答案。

### Process Reward Model

对每一步进行判断，可更早剪掉错误分支。

### Domain Verifier

代码测试、数学等价、形式证明等可直接执行验证。

Test-time scaling 的效果高度依赖 verifier。没有可靠选择器，多生成只会产生更多候选错误。

## 19. 计算最优分配

固定总计算预算：

$$
C_{\text{total}}
=
C_{\text{pretrain}}
+C_{\text{test}}.
$$

问题不是永远选择最大模型，而是根据难度在：

- 模型规模；
- 样本数；
- 修订步数；
- 搜索宽度；
- verifier 成本

之间分配。

小模型配合智能 test-time compute 在一些任务上可超过更大模型的标准解码。

## 20. 小结

- Speculative sampling 用 rejection correction 保持 target 分布，同时减少串行大模型调用。
- Online/offline 描述能否继续交互，on/off-policy 描述数据是否来自当前 policy。
- 异步 LLM RL 提高吞吐，也会制造 stale rollout 与有偏梯度。
- On-policy distillation 在 student 自身状态上提供 teacher 的稠密信号。
- RoPE 将相对位置编码进 Q/K 点积，位置缩放与长数据训练共同扩展上下文。
- Test-time compute 只有与有效 verifier 和计算分配结合时才有稳定收益。
